## Work done (MQL5 only, as asked)
**Three new inputs in `mql5/BprFvgEA/BprFvgEA.mq5`, version 3.00.** All default to `true`, so v3 behaves exactly like
v2. A fourth input, `InpEntriesAfterSessionEnd`, was added after the review (see below).

| Input | When `false` |
|---|---|
| `InpUseCostFilter` | The executor passes `maxCostR = 0` (off) to the detector. No `SKIP (COST)`. |
| `InpUseRRFilter` | The executor passes `minRR = 0` (off). No `SKIP (RR)`. Note that `InpMinRR` already defaults to 0. |
| `InpCancelAtSessionEnd` | `BuildEnv` no longer sends the 14:45 cancel; after the review it sends only the rollover cut (see below). Pending orders are not cancelled at 14:45 New York and stay until they fill, the leg expires, a new extreme re-anchors the setup, or 16:44 New York arrives. |

**Unchanged:**
- **The entry window.** New orders after 14:45 still need `InpUseSession = false`.
- **The 16:44–17:00 New York rollover deletion of pending orders.** A fill there would be closed at once by the 16:44
  flat. It now logs `ROLLOVER` explicitly and is counted on the panel. Its record reason stays `SESSION_END`, so the
  pure codes are unchanged.
- **The hard limits:** 0.20 % per setup, 1 % daily, 120-min time stop, tester / demo only.

**Other changes:**
- **Visibility.**

  - A `start v3:` log line.
  - A `SELF-CHECK switches` line, plus a note when the cost filter is off.
- **The pure detector and the Python reference are unchanged.** The switches are mapped in the executor. The parity
  harness therefore still covers the default rules, and the cost and RR switches equal `max_cost_r = 0` /
  `min_rr = 0` in the reference.
- **Docs:**

## Adversarial review (workflow: 2 reviewers + 2 skeptics)
**Result.** Compile: no errors found. Behaviour: 7 findings, 4 confirmed (all low), 3 refuted.

### Fixed
1. **No tick in the rollover window.** With `InpCancelAtSessionEnd = false`, a pending order could survive into the
   next FX day when no tick came between 16:44 and 17:00 New York:
   - a data gap;
   - a disconnect;
   - "Open prices only" mode on M30 or above;
   - GTC orders on symbols that refuse an expiry time.

   The executor now sends a **bar-based rollover cut** (`RolloverCut`) as the session-cancel signal: the next bar
   opens at or after 16:44 New York, on a weekend, or in another FX day. This needs no tick.
2. **Misleading switch display.** The line showed "cancel at 14:45 ON" with `InpUseSession = false`. It now shows the
   setting that actually applies.
3. **Counters not reset** after a re-init (input or chart change): `g_nRollDel`, `g_nExpPre` and `g_nExpLeg`.
4. **Docs.** The spec header and the §1 table still said v2. README step 6 now names the switches.

### Added
**`InpEntriesAfterSessionEnd`** (default false). The owner asked "so the EA can place order even if … session end",
but `InpCancelAtSessionEnd` only keeps orders that already exist. The new switch extends the entry window for **new**
orders to 16:44 New York, Mon–Fri, and keeps the 08:00 London start. With `InpCancelAtSessionEnd = true`, orders are
then cancelled at the end of the extended window. This came from a refuted finding (refuted as a defect, but it is the
owner's literal wording). It is implemented in the executor (`BuildEnv`, `LateEntryOk`), with no detector change.

### Refuted (no change)
- Records of the rollover delete still say `SESSION_END`. This is documented and the log says `ROLLOVER`.
- The CSV does not tag the switch state. That was already true in v2; trials are counted in the trial registry.

### Re-test after the fixes
- `PYTHONPATH=.:tests pytest --noconftest -q tests/test_bpr_breakout_ea_harness.py tests/test_bpr_breakout_strategy.py
  tests/test_bpr_fvg_ea_harness.py` gives **141 passed**.
- `tools/mql5_static_check.py mql5/BprFvgEA` reports no unknown names and balanced brackets.

## Final verification of the fixes (workflow: verifier + skeptic)
4 findings, 3 confirmed, all fixed. Defaults still give v2's detector decisions.

1. **A fill on the first tick after the rollover** (medium).
   - **Problem.** With no tick in 16:44–17:00 New York, a pending order could fill on the first tick after 17:00,
     before any bar-based cut ran, and be held in the next FX day.
   - **Fix.** The limit order's server-side expiry is capped at the next 16:44 New York, for all settings; the broker
     removes the order without needing a tick. No new order is sent in the last 2 minutes before 16:44.
2. **The extended window had no gap check** (low).
   - **Problem.** With `InpCancelAtSessionEnd = true` and the extended window, a data gap into the next day's window
     did not cancel the orders.
   - **Fix.** `sessionCancel` also fires on a new FX day, but only when `InpEntriesAfterSessionEnd = true`, so the
     defaults stay identical to v2.
3. **The SELF-CHECK window was wrong across server midnight** (low), for example with a fixed UTC+3 in US winter.
   - **Fix.** It now prints the first window that starts on that server date, with "(+1 day)" when its end falls on
     the next date.
   - **Check.** A zoneinfo simulation gives:
     - fixed +3, January: 11:00 → 00:43 (+1 day);
     - NY+7: 10:00 → 23:43 with the extended window, and 10:00 → 21:44 without it.
4. **The README rollover sentence** (refuted).
   - The skeptic refuted it as a defect: with `InpUseSession = false` no window applies.
   - The README now spells out every rollover protection anyway.

## Limitations
- **Not compiled in MetaEditor.**
- **Using any switch is a new trial** for research purposes. With the cost filter off, entries on small Fibonacci legs
  can have costs that are a large share of their risk.

## Conflict with a hard rule (recorded before the change)
`CLAUDE.md` says "every position closed ≤ 120 minutes after entry". The owner explicitly asked to make that exit
switchable. Decision, as told to the owner:

- switched off, it is the owner's decision for the Strategy Tester / demo accounts (real accounts stay log-only);
- a run with a switch off is **not a research trial of H-14** and cannot support any claim about it. The panel and the

- `InpMaxHoldMin` keeps its 120-min cap.

## Work done (MQL5 only)
`mql5/BprFvgEA/BprFvgEA.mq5`, version 4.00:

| Input | Default | When `false` |
|---|---|---|
| `InpUseTimeStop` | true | No `close at market: TIME`. The position runs to its SL / TP (or the 16:44 flat). |
| `InpFlatBeforeRollover` | true | No `close at market: ROLLOVER` at 16:44 New York. Positions may cross the rollover and the weekend. |

- `TimeStopDue` / `RolloverFlatDue` gate every market close of those two kinds:

  - a partly filled order's position;

    in that window;

  EA-11 and U-15.

## Adversarial review of v4 (workflow: 2 reviewers + 1 skeptic per finding)
The first run was cut by the session limit before any agent finished, and was re-run after the reset.

**Result.** Compile: no findings. Behaviour: 7 findings, 5 confirmed, 2 refuted.

### Fixed
1. **Daily loss of a position held more than 4 days** (medium).
   - **Problem.** `CBfRisk::Recompute` reads 4 days of history and counts today's deals only for positions whose EA
     entry deal is in that window. With both switches off, a position filled Thursday and stopped Monday was missing
     from the daily loss: no lockout, and `today: 0.00` on the panel.
   - **Fix.** Today's deals of positions with no EA entry deal in the window are looked up by position
     (`OlderPositionToday`, `HistorySelectByPosition`) and counted when this EA opened them. With the defaults only
     other programs' positions are looked up, and they add 0, so the result is unchanged.
2. **The self-check note was wrong with only one switch off** (low). There is now one note per switch combination.
3. **Log texts assumed both exits on** (low):
   - the rollover wait now reads `no new order over the rollover`;
   - closing a position at removal names the exits that would stop running;
   - partial-fill and orphan closes now say which exit fired;
   - the `AddOrphan` text has correct grammar.
4. **Time stop with only the flat off** (low, docs). The time stop can fall after 16:44 New York (in the rollover
   spread) or after the Friday close, when the close waits for the reopen. This is now in the README and spec §8.
5. **README "hard limits" wording** (low). The 120-min / 16:44 exits moved out of the "no input can raise" list into a
   "default exits" bullet.

### Refuted (no code change)
- **Re-attaching the EA with a switch on closes old positions at once.** This is v3 behaviour, and it is intended. A
  README sentence was added anyway.
- **"Hard rule" label wrong with only the flat off.** Refuted: the 120-min deadline can then fall after the Friday
  close. The label now reads `H-14 exits changed`.
