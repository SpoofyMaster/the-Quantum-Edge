# Day 08 — 2026-10-11 — BprFvgEA v5: anticipated entries and a close-based leg break

## Request (owner)
> "i noticed again that the EA didnt place orders and the reason is LEG_BROKEN, but sometime this broken leg is the
> retracement so when price pulls back the EA didnt anticipate it and place the limit orders, so for this i want you
> add this changes on the input to allow the EA placing orders even if the price pulls back quickly and broke leg.
> WORK ONLY on MQL5 code and give me the v5"

## Diagnosis (from the code; no MT5 log was sent)
- **When v4 decides.** After the confirmation (phase `LEG`), v4 decides the limits only on a **closed pullback candle**
  (a candle without a new extreme, with an FVG after the reference candle). It sends them at the **next candle's
  open**.
- **What goes wrong.** Sometimes one candle falls from the leg high through 50 / 61.8 / 71 % and below the leg origin
  `O`. The retracement is then over before any order exists, and that candle's low below `O` ends the setup:
  `DONE(LEG_BROKEN)` (spec §4.2 step 1).
- **The same after a re-anchor.** A new high cancels pending limits (`NEW_EXTREME`) and waits for the next pullback
  candle, so a sharp reversal right after the leg's last high has no order in the book either.
- **In the harness.** `tests/bk_scenarios.py` `leg_broken` (bar 19) and the new `fast_pullback` sequence (bars 20–21)
  both reproduce it.

## Work done (MQL5 only, as asked)
**Two inputs in `mql5/BprFvgEA/BprFvgEA.mq5`, version 5.00. Both default to `false`, which is v4.**

| Input | Detector param | When `true` |
|---|---|---|
| `InpAnticipateEntries` | `anticipate` | See below. |
| `InpLegBreakOnClose` | `legBreakOnClose` | `originBroken` uses the close instead of the low (long) / high (short), in `LEG` and `ORDERED`. |

**What `InpAnticipateEntries` changes.**
- **Decision bars.** The confirmation bar and every leg bar are decision bars, new extreme or not. The FVG condition
  is still required.
- **New extreme while orders are pending.** The limits are cancelled (`NEW_EXTREME`) and decided again on the **same
  bar** at the new Fibonacci.

**Same-bar slot.**
- **The problem.** The slot (one setup with orders) was busy when the bar closed, held by the setup's own limits.
- **The fix.** `BfEnv.slotOwner` names the setup whose healthy pending limits alone hold it. `Decide` lets only that
  setup decide on that bar; the others count as `blocked slot`.
- **Executor.**
  - `SlotOwner()` sets the env field. It returns 0 with a position, an unowned position, another order, or a level
    being deleted or partly filled.
  - `ExecCancel` marks server-confirmed deletes (`deleted`).
  - `ExecBatch` checks `SlotFreeFor(id)`. It ignores the context's own just-deleted orders that the terminal may still
    list, and nothing else.
  - A failed delete, or an old order that filled first, keeps the slot busy. Nothing new is sent and the setup
    decides again later (`NotifyRetry`). Old and new limits of one setup can therefore never both fill, and the 0.20 %
    per setup holds.

## What it does and does not deliver (told to the owner)
- **`InpAnticipateEntries` delivers the fast pullback.** In the harness, the owner's case changes from
  `DONE(LEG_BROKEN)` with no trade to three fills.
- **A pullback through the stop is now a loss.** The stop is `O − 10 ticks`, so a pullback that breaks the origin by
  more than that **stops the fills out**; before, it was a no-trade. Widening `InpStopFib` or `InpStopBufferTicks`
  gives room, and the lots shrink with the stop distance.
- **`InpLegBreakOnClose` alone does not deliver it.** Entries above the wick candle's close are `MISSED`.
- **Order churn.** Up to 6 trade requests per new-high candle on M1.
- **Research status.** Either switch is a new rule set, not H-14.

## Adversarial review (workflow: 3 reviewers + 1 skeptic per finding)
**Lenses.** MQL5 compile-readiness, executor safety, detector logic and owner intent.

**Result.** Compile: no findings. 8 findings: 4 confirmed, 4 refuted.

### Fixed
1. **Partial fill in the same tick as a move** (medium, executor).
   - **Problem.** An old limit could fill partly just before its delete, and the terminal might not list that
     position yet. The new batch would then go out with the full 0.20 % budget beside the hidden part: about 0.24 %
     for the setup, and on netting one position managed twice.
   - **Fix.** `SlotFreeFor` first requires the history order of every level deleted on this tick to show no filled
     volume. If that is not proven, the EA waits (`NotifyRetry`), and the setup decides on a later bar after
     `SyncTrade` / `Reconcile`. `SlotOwner` also returns 0 while a tracked order is partly filled.
2. **Moves ignored the leg expiry and the session cancel** (medium, detector).
   - **Problem.** The `ORDERED` re-anchor marked the setup ready before the expiry and session-cancel checks, so
     limits could be placed after `InpLegExpiryBars`, without limit in a trending leg.
   - **Fix.** The re-decision now needs `u − confirmBar ≤ leg_expiry_bars` and no session cancel. The next `LEG` bar
     ends the setup as in v4.
3. **A spike on an extra decision bar ended the setup** (low, detector).
   - **Problem.** A spike candle closing beyond every entry on the confirmation or a new-extreme bar ended the setup
     `DONE(NO_LEVEL)`, while v4 would trade the next pullback candle.
   - **Fix.** On those bars only, an all-`MISSED` result records nothing and the setup stays in `LEG`.
4. **The switches-off test compared v5 with itself** (low, tests).
   - **Fix.** The new sequences moved to `tests/bk_scenarios.py` `v5_sequences()` and joined the Python parity set
     (long and mirrored, 3 FVG rules plus strict). There the switches-off EA equals the v4 reference (+72 parity
     cases).

### Refuted (no code change)
- **Ghost listing of a deleted order after `ResetCtx`.** It is v4 behaviour and harmless: `Reconcile` never used the
  marker.
- **`legBreakOnClose` has no effect in `ORDERED`.** That path is unreachable in v4 too. The README now says that the
  origin and the stop are kept.
- **README overstates the delivery.** The FVG condition is stated each time. The README now spells out the LuxAlgo
  timing as well.
- **The harness fixes the session gates.** That is long-standing. Optional `sess_cancel` / `sess_off` keys were added
  to `bk_main.cpp` anyway, and tests use them.
