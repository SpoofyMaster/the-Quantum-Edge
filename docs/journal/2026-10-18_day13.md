# Day 13 — 2026-10-18 — BprFvgEA 9.01: InpCancelAtSessionEnd = false keeps the pending orders

## Request (owner)
> "there is one bug on the code, when i set on the input : cancel pending orders at 14:45 New York rollover on FALSE, it
> keeps canceling pending orders so please do not change nothing, focus only to fix this bug making the EA not
> canceling pending orders"

## What 9.00 did with `InpCancelAtSessionEnd = false`
No cancel at 14:45, as documented since v3. Four other paths still removed pending orders for a time reason:
1. **The detector's rollover cut.** `BuildEnv` set `env.sessionCancel = RolloverCut(...)`. It was true when the next bar
   opened at or after 16:44 New York, on a weekend or on a new FX day. The detector then cancelled the levels
   (`CANCEL / DONE (SESSION_END)`).
2. **The EA's rollover delete.** `SyncTrade` deleted every pending order on a tick between 16:44 and 17:00 New York,
   whatever the switch ("ROLLOVER: the pending order is deleted").
3. **The broker-side expiry.** Every limit was sent with an expiry capped at the next 16:44 New York.
4. **A move after 14:45.** A new high / low in `ORDERED` cancelled the levels to move them (the re-anchor). The move
   could not be sent (no new order outside the entry window), so the orders were lost.

Paths 1-3 were the documented v3 rollover rule. The owner's report overrides it for the switch `false`.

## 9.01 (only with `InpCancelAtSessionEnd = false`; the default `true` is unchanged)
- **Detector cancel.** `env.sessionCancel = false`. The unused `RolloverCut` is removed.
- **Rollover delete.** The 16:44-17:00 delete and the 16:44 expiry cap apply only with the switch `true`.
- **Expiry over closures.** The leg-expiry server-side expiry gets 3 more days. It counts clock time; the detector's
  leg expiry counts bars, and a weekend or a daily break forms none.
- **No move when it cannot be sent.** New `BfEnv.keepOrders`, set by the EA when no order can be sent:
  - when: outside the entry window (with `InpUseSession`), in the last 2 minutes before 16:44, or in 16:44-17:00;
  - checked at this bar's decision, at the next bar (a move that has to wait or be retried) and now (a bar replayed
    after a reconnect); helper `NoOrderAt`;
  - effect: the detector's `ORDERED` branch skips the re-anchor, so the levels stay where they are, and the leg-broken
    / leg-expiry / target rules still apply;
  - inside the entry window nothing changes.
- **Executor texts.** The input comment, the self-check switch text and the version (9.01).
- **Harness.** Keys `sess_off_from` and `keep_orders`.

## Review (workflow: 2 reviewers + skeptics)
- **The skeptics failed** on a session limit. I checked the 7 findings myself, against the code and the reviewers'
  harness runs.
- **Fixed (real):**
  - **Bars replayed after a reconnect across 14:45.** A replayed bar from before 14:45 still moved the orders, and the
    move could never be sent. `keepOrders` now also checks the current time.
  - **Clock-time expiry.** Kept orders could expire over a weekend or a daily break before the leg ends: 3 days of
    slack.
  - **A move on the last bar before the window ends** that has to be sent or retried on the next bar. The next bar is
    now checked.
- **Documented, not fixed:**
  - **Inputs and restarts.** Changing inputs, timeframe or symbol, recompiling or restarting deletes the EA's pending
    orders (OnDeinit, restart cleanup, stray-order rule). It is not a time rule, and a fix needs the EA to adopt its
    old orders after a restart, which is outside a one-bug fix.
  - **`InpAnticipateEntries = false`.** A move takes the orders off the market until the next pullback candle (the
    v4 rule). If the window ends before it, they are not sent again.
